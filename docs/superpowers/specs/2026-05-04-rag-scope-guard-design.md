# RAG 问答领域范围收口设计

- 日期：2026-05-04
- 主题：仅限制 `rag/ask` 接口只回答健身、饮食及扩展相邻主题
- 状态：已评审通过，待用户审阅文档后进入实现计划

## 1. 背景与目标

当前项目的 AI 服务位于 `apps/ai-service`，其中：

- `POST /api/v1/rag/ask` 承担自由问答能力
- `POST /api/v1/diet-plans/explain`、`POST /api/v1/training-plans/explain`、`POST /api/v1/plans/adjust` 承担结构化解释与改计划能力

本次需求不是收紧整个 AI 服务，而是只限制 `rag/ask`：

- 接入真实 AI，使用 OpenAI 官方 API
- 仅允许回答健身、饮食及扩展相邻主题
- 当用户提问超出范围时，不做硬报错，改为软拒绝并引导用户改问
- 现有结构化接口保持原样，不受本次范围限制

## 2. 范围定义

### 2.1 本次改动范围

仅改动以下链路：

- `apps/ai-service` 中 `AIOrchestrator.rag_ask()`
- `rag/ask` 相关的领域判定、配置、提示词、测试
- OpenAI 官方模型 provider 接入

### 2.2 明确保留不动

以下接口和能力不收紧：

- `diet-plans/explain`
- `training-plans/explain`
- `plans/adjust`
- 现有规则引擎改计划逻辑

### 2.3 允许回答的主题

允许范围采用扩展版，包含但不限于：

- 训练安排、动作执行、训练容量、肌群刺激
- 饮食结构、热量、宏量营养素、食材替换
- 减脂、增肌、体重管理
- 恢复、睡眠、训练后恢复建议
- 基础补剂建议
- 轻度运动康复
- 轻度疼痛处理与训练调整

### 2.4 不允许回答的主题

以下主题不属于 `rag/ask` 的可回答范围：

- 编程、法律、金融、历史、娱乐、购物、情感等通用问答
- 与健身饮食无明显关系的百科类问题
- 与当前产品定位无关的泛化陪聊

### 2.5 高风险优先拦截

以下主题不进入“软拒绝”流程，而是继续由现有 `SafetyService` 高优先级拦截：

- 医疗诊断与治疗建议
- 处方、用药、激素、疾病管理
- 严重疼痛或伤病判断
- 自残、自杀
- 极端减重、断食、催吐、泻药、脱水等高风险内容

结论：安全拦截优先级高于领域范围判定。

## 3. 总体方案

采用混合判定方案：

1. 先做输入安全检查
2. 再做规则粗筛
3. 对规则无法稳定判断的问题，调用一次模型做范围分类
4. 只有判定为范围内的问题，才进入现有 RAG 检索与生成
5. 范围外问题直接返回软拒绝文案与引导提问

该方案兼顾三点：

- 明显越界问题能快速短路，降低成本
- 边界问题不至于被简单关键词误杀
- 不需要重做现有 `rag/ask` 的主体生成链路

## 4. 目标流程

`rag/ask` 新流程如下：

1. `input_safety`
2. `domain_scope_gate`
3. `question_classification`
4. `knowledge_retrieval`
5. `answer_strategy`
6. `llm_generation`
7. `output_safety`

其中新增的 `domain_scope_gate` 行为如下：

- `in_scope`：继续后续流程
- `out_of_scope`：直接返回软拒绝响应
- `uncertain`：调用范围分类模型二判，再决定是否继续

## 5. 领域判定设计

### 5.1 新增服务

新增一个领域判定服务，建议命名为 `DomainScopeService`。

职责：

- 只负责判定 `rag/ask` 问题是否属于允许领域
- 不负责生成正式答案
- 输出结构化结果，供 orchestrator 决策

建议输出：

- `label`: `in_scope` | `out_of_scope` | `uncertain`
- `reason`: 判定原因
- `matched_signals`: 命中的规则或分类信号

### 5.2 第一层：规则粗筛

规则粗筛负责处理两类情况：

- 明显属于健身饮食领域的问题，直接放行
- 明显与健身饮食无关的问题，直接拦截

规则设计要求：

- 使用小规模关键词、短语和主题模式
- 优先可解释、易维护
- 不追求覆盖所有边界情况

建议信号：

- 明确放行词：训练、动作、增肌、减脂、热量、蛋白质、饮食、补剂、恢复、睡眠、拉伸、酸痛、体重、康复训练等
- 明确拦截词：代码、编程、股票、基金、法律、合同、旅游、感情、写作业、八卦、买车等

### 5.3 第二层：模型分类

当规则粗筛无法稳定判断时，标记为 `uncertain`，再调用模型做领域分类。

分类模型要求：

- 只输出结构化分类结果
- 不输出正式回答
- 提示词足够短，降低成本与不确定性

示例输出：

```json
{
  "label": "in_scope",
  "reason": "用户在问熬夜对训练恢复和增肌效率的影响"
}
```

### 5.4 领域边界原则

边界问题按以下规则处理：

- 睡眠影响训练或减脂：范围内
- 轻度疼痛与训练调整：范围内
- 康复训练和负荷调整：范围内
- 伤病诊断、影像解读、药物治疗：安全拦截
- 完全无关的日常问题：范围外软拒绝

## 6. 软拒绝策略

### 6.1 选择理由

本次采用软拒绝，而不是硬拒绝。

原因：

- 更符合产品对话体验
- 能把用户重新引回目标领域
- 不会让用户感觉系统“只会报错”

### 6.2 响应格式

越界时不新增新接口类型，继续复用现有 `RagAnswerPayload`。

- `answer`：放统一软拒绝文案
- `tips`：放 2 到 3 个引导提问示例
- `risk_note`：通常为空；若涉及轻度疼痛边界，可补“非医疗建议”提醒
- `citations`：空数组
- `trace`：新增 `domain_scope_gate`

这样可以保证：

- `apps/api` 无需大改
- 前端不必为新响应协议做分叉处理
- 统计越界比例时可直接基于 `trace`

### 6.3 软拒绝文案原则

软拒绝文案固定包含三部分：

1. 说明问题超出当前范围
2. 说明当前可以回答什么
3. 给出 2 到 3 个改写示例

示例方向：

- “熬夜后今天训练要不要减量？”
- “膝盖轻微酸痛时腿部训练怎么调整？”
- “减脂期晚餐怎么安排蛋白质和主食？”

## 7. OpenAI 官方接入设计

### 7.1 provider 策略

在现有 `BaseLLMClient` 抽象下新增官方 provider，建议命名为 `OpenAILLMClient`。

不直接覆盖当前 `openai_compatible` 的原因：

- 保留兼容网关能力
- 未来切回代理层时不需要回滚架构
- provider 语义更清晰

### 7.2 配置项

建议新增或规范化以下配置：

- `AI_PROVIDER=openai`
- `OPENAI_API_KEY`
- `OPENAI_MODEL`
- `OPENAI_BASE_URL`，默认可指向官方地址
- `AI_SCOPE_MODEL`，可选；未配置时回退到 `OPENAI_MODEL`

### 7.3 默认模型策略

本次用户选择“均衡优先”，默认建议：

- 正式问答模型：`gpt-4.1-mini`
- 领域分类模型：优先使用更轻量模型；若不单独配置，则复用正式问答模型

### 7.4 调用约束

OpenAI provider 仍走当前的聊天消息编排方式：

- `system_prompt`
- `user_prompt`

这样可以最大限度复用现有提示词与输出修复逻辑。

## 8. 提示词设计

新增两类提示词：

### 8.1 范围分类提示词

新增任务模板，例如 `scope_classification_task`。

要求：

- 只做分类
- 不做正式回答
- 输出固定 JSON
- 明确允许范围、拒绝范围与高风险排除原则

### 8.2 软拒绝模板

新增统一软拒绝模板，例如 `out_of_scope_reply`。

要求：

- 语气明确但不生硬
- 明确当前支持的主题
- 给出可立即复问的示例

## 9. 代码改动边界

建议变更点如下：

- `app/services/orchestrator.py`
  - 在 `rag_ask()` 中插入 `domain_scope_gate`
- `app/services/`
  - 新增 `domain_scope.py`
  - 新增或扩展 LLM provider 实现
- `app/core/config.py`
  - 增加 OpenAI 官方 provider 配置
- `app/services/container.py`
  - 挂载新的 provider 和领域判定服务
- `app/prompts/`
  - 新增范围分类与软拒绝模板
- `apps/ai-service/tests/`
  - 新增范围判定与 provider 配置测试

## 10. 测试策略

本次实现必须覆盖以下测试类型。

### 10.1 领域内放行

示例：

- 饮食替换
- 训练安排
- 睡眠与恢复
- 补剂基础建议
- 轻度膝盖酸痛下的训练调整

预期：

- `domain_scope_gate` 放行
- 正常进入检索和生成

### 10.2 明显越界软拒绝

示例：

- 写代码
- 法律咨询
- 股票建议
- 通用闲聊

预期：

- 不进入正式 RAG 生成
- 返回统一软拒绝文案
- `trace` 包含 `domain_scope_gate`

### 10.3 高风险安全拦截

示例：

- 糖尿病用药
- 激素
- 严重疼痛诊断

预期：

- 继续由 `SafetyService` 拦截
- 不进入领域软拒绝逻辑

### 10.4 边界问题

示例：

- “熬夜后能不能练？”
- “肩膀有点不舒服今天怎么练？”

预期：

- 先经过混合判定
- 不因单一关键词策略被误杀

### 10.5 配置缺失

示例：

- 选择 `openai` provider 但缺少 API key

预期：

- 返回明确配置错误
- 不静默回退到 mock

## 11. 风险与对策

### 11.1 误杀与漏判

风险：

- 规则过严会误杀边界问题
- 规则过松会放过无关问题

对策：

- 使用 `uncertain -> 模型二判`
- 保持规则词表小而清晰

### 11.2 轻度疼痛与医疗边界混淆

风险：

- 用户提问可能介于训练调整与医疗咨询之间

对策：

- 安全拦截优先于领域判定
- 轻度疼痛只回答训练调整，不给诊断与治疗建议

### 11.3 模型调用延迟增加

风险：

- 边界问题会多一次分类调用

对策：

- 只对 `uncertain` 触发分类
- 明显越界问题直接规则短路

## 12. 实施顺序建议

建议按以下顺序落地：

1. 先为领域范围判定写测试
2. 实现 `DomainScopeService`
3. 把 `domain_scope_gate` 接入 `rag_ask`
4. 新增 OpenAI 官方 provider
5. 新增提示词模板
6. 跑 AI service 测试
7. 做一次端到端问答验证

## 13. 非目标

本次明确不做：

- 重构整个 AI 服务架构
- 改写结构化饮食/训练解释接口
- 引入复杂的多轮记忆策略
- 扩展到全域通用助理
- 处理医疗诊断场景

## 14. 验收标准

当满足以下条件时，可视为本次设计目标完成：

- `rag/ask` 仅回答健身、饮食及扩展相邻主题
- 越界问题返回软拒绝与引导提问
- 高风险问题继续由安全规则拦截
- 其他 AI 接口行为不变
- OpenAI 官方 API 可通过配置启用
- 范围判定和配置缺失均有自动化测试覆盖
